## 2026-07-07 Cloudflare Pages Direct Upload 不能原地转 Git 集成

### 现象

项目已通过 `wrangler pages deploy` 直接上传上线，随后尝试用 Cloudflare Pages Project API 给同一个 Pages 项目补充 GitHub `source`，API 返回：

```text
You cannot update the source object in a Direct Uploads project.
```

### 原因

Cloudflare Pages 的 Direct Upload 项目和 Git Integration 项目类型不同，现有 Direct Upload 项目的 `source` 不能被原地更新为 GitHub 仓库。

### 解决方案

- 已保留当前线上 Direct Upload 项目，避免影响 `https://palworld-1-0-guide-hub.pages.dev/`。
- 已完成 GitHub `main` push，并设置 Cloudflare Pages `PUBLIC_SITE_URL` 普通环境变量。
- 如需同名 Git 集成，需要先删除当前 Direct Upload 项目，再创建同名 Git 集成项目。
- 如不想影响当前线上站，可以新建另一个 Git 集成 Pages 项目。
- 用户确认站点尚未正式推广后，已删除旧 Direct Upload 项目并重建同名 GitHub 集成 Pages 项目；Cloudflare 项目列表显示 `Git Provider: Yes`。
- 重建后需要触发一次 production deployment；本项目通过 Cloudflare Pages deployments API 触发并成功部署。
- API 创建的 Git source 项目没有响应后续 GitHub push 自动部署；最终确认原因是 Cloudflare Workers and Pages GitHub App 只授权了旧仓库 `china-travel-guide`，没有授权当前仓库 `palworld-1-0-guide-hub`。
- 用户登录后，在 GitHub App 安装页把 `zsq378554827/palworld-1-0-guide-hub` 加入 selected repositories 并保存。随后 push commit `4028de7`，Cloudflare Pages 自动生成 `github:push` production deployment `266a3200` 并部署成功。

### 是否值得写入全局踩坑日志

值得。以后内容站如果最终要 Git 自动部署，应优先通过 Dashboard/API 创建 Git Integration 项目，不要先创建同名 Direct Upload 项目。

## 2026-07-12 YouTube Unlisted 嵌入仍要求登录

### 现象

YouTube Unlisted 视频通过 `youtube-nocookie.com` 嵌入后，自动化浏览器和真实访客都看到“请登录，以便确认你不是聊天机器人”。

### 原因

Unlisted 只控制发现性，`youtube-nocookie.com` 只减少 Cookie/跟踪；两者都不保证匿名播放。

### 解决方案

- 站内主播放器改为自托管 H.264/AAC HLS，YouTube 只保留后台备份。
- 使用原生 `<video>` + `hls.js`，VideoObject 改用 HLS `contentUrl`。
- 线上未登录浏览器验证实际播放时间增加和章节跳转，而不是只检查 DOM。

### 是否值得写入全局踩坑日志

值得，已写入全局踩坑日志第 15 条和 `localize-short-video` Skill。

## 2026-07-13 没有自有域名不等于无法使用私有 R2

### 现象

原迁移方案把“R2 Standard + 自有媒体子域名”一起列为第四条视频上线前置条件，但用户没有自有域名。

### 原因

自有媒体子域名只是缓存、品牌和后续迁移的优化项，不是 Pages 读取 R2 的技术必需条件。

### 解决方案

- 在 Pages Functions 中绑定私有 R2 bucket，通过现有站点同源 `/media/...` 输出 HLS。
- 保留 GET/HEAD、Range、ETag、Cache-Control、MIME 和 CORS 行为。
- 用户启用 R2 Standard 后创建 `palworld-guide-media`，无需购买域名即可继续生产部署。
- R2 未启用且可能计费时，不代用户开通；本地代码和媒体可先准备完毕。

### 是否值得写入全局踩坑日志

值得，适用于所有 Cloudflare Pages + 私有 R2 媒体站。

## 2026-07-14 大体积 Pages 部署记录出现后媒体仍可能尚未传播完成

### 现象

第四条约 157 MB HLS push 后，Cloudflare 已显示新的 production deployment，但生产主域名暂时把新页面和媒体路径回退为首页，部署专属域名的新媒体路径暂时为 404。

### 原因

GitHub push、构建记录创建、静态资源上传和生产别名传播不是同一时刻完成。大体积媒体比普通页面需要更长时间，不能只看 deployment 已出现或列表中的 `Active`。

### 解决方案

- 等待部署专属域名上的新页面、缩略图、manifest、init 和首个分片全部返回 200 与正确 MIME。
- 再检查生产主域名完成同样切换；缺失路径返回首页 HTML 时不能视为媒体成功。
- 最后用未登录浏览器确认 `readyState`、`duration`、`currentTime` 前进和章节跳转。
- 本次约等待 5 分钟后资源传播完成；下一个视频改用 R2，避免继续拉长 Git/Pages 媒体部署。

### 是否值得写入 Skill

值得，已加入 `localize-short-video` 的部署验收门槛。
